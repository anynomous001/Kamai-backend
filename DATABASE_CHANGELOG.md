# DATABASE_CHANGELOG.md — Kamai Backend OMS

> Documents all Prisma schema changes and migrations in chronological order.

---

## [v1.0.1] — 2026-07-29 — Orders display_id: per-tenant, not platform-wide

### Summary

Corrects a v1.0.0 deviation: `orders.display_id` was generated from a
single sequence shared across every baker, so order codes reflected
platform-wide order volume rather than each baker's own. Migration
`prisma/migrations/20260729010000_orders_per_tenant_display_id` replaces
the global-sequence trigger for `orders` only (bakers/customers/
investments/payment_events/inventory_items are unaffected and keep their
existing global-sequence behavior) with a per-baker counter table
(`order_display_id_counters`, keyed by `baker_id`) updated via an atomic
`INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`, so concurrent
inserts for the same baker serialize on the row lock instead of racing.
`orders.display_id` uniqueness is now scoped to `(baker_id, display_id)`
instead of global — two different bakers can both have an `ORD-000001`.
Verified with a manual concurrent-insert check: baker A got
`ORD-000001`/`ORD-000002`, baker B independently got its own
`ORD-000001`.

## [v1.0.0] — 2026-07-29 — Baker Operations Platform v2 Redesign

### Summary

Full redesign of the Baker Operations tables. Replaces `Baker`/`Customer`/`Order`/
`PaymentLedger`/`Investment` with `bakers`/`customers`/`orders`/`payment_events`/
`investments` (snake_case DB columns via `@map`, camelCase Prisma/TS fields kept
so application code shapes didn't need to change just because the DB did), plus
a new `inventory_items` table. Migration:
`prisma/migrations/20260729000000_baker_ops_v2_redesign`. No live data existed
in these tables at migration time (one dev-test `Baker`/`RefreshToken` row was
cleared as part of the migration).

### Key changes

- **`display_id`**: every one of the 6 tables gets a human-readable code
  (`BAKER-001`, `CUS-0001`, `ORD-000001`, `INV-0001`, `PAY-000001`, `ITM-0001`)
  generated by a Postgres sequence + `BEFORE INSERT` trigger, replacing the
  old in-process random `orderNumber` generator.
- **Money**: switched from integer paise to `numeric` rupees across every
  baker-ops table.
- **Status/category fields**: `text` + `CHECK` constraint instead of native
  Postgres enums, for `order_status`, `payment_status`, `delivery_type`,
  `bakers.status`, `bakers.subscription_status`, etc. — vocabulary can now
  evolve without a schema migration. `bakers.subscription_status` keeps its
  full 6-state vocab (`TRIAL/PENDING/ACTIVE/PAUSED/CANCELLED/EXPIRED`,
  ALL_CAPS preserved) because the Razorpay webhook processor's state map
  depends on all 6 — only `orders`/`payment_events` adopted the new
  Title-Case vocab (`Pending`, `Confirmed`, `In Progress`, ...).
- **`customers`**: `lifetimeValue`/`totalOrders`/`lastOrderDate` are no
  longer stored — always computed from `orders` at query time (excluding
  Cancelled orders, matching the old recalculation's exclusion rule). Phone
  is now nullable; upsert-by-phone only applies when a phone is provided.
- **`orders`**: no more `deletedAt` soft-delete — Cancelled is a first-class
  `order_status` value and the sole source of truth for cancellation. New
  fields: `weight_in_pounds`, `quantity`, `occasion`, `custom_instructions`,
  `delivery_type`/`delivery_time`/`delivery_charge`, `custom_fields` (jsonb,
  max-10 enforced at the app layer), `internal_notes`. Payment-status
  derivation is now a single shared rule (advance vs total price) applied
  consistently at creation, edit, and balance-payment time.
- **`payment_events`** (replaces `PaymentLedger`): `event_type`
  (`advance_received`/`balance_received`/`refund`) replaces the old
  `type` (CREDIT/DEBIT), which was redundant once `event_type` existed.
  `payment_mode`/`transaction_reference` preserved as real columns (required
  `payment_mode`, optional `transaction_reference`) — not in the original
  spec draft, added back after confirming the live `PaymentLedger` required
  a payment mode. The denormalized `orderNumber` copy was dropped (`order_id`
  + `orders.display_id` join covers it).
- **`investments`**: kept as a per-material purchase ledger (materialName/
  quantity/unit/pricePerUnit/totalCost/supplierName), `category` and
  `description` added alongside rather than replacing those fields.
- **`inventory_items`**: new table, no prior equivalent.
- **RLS**: intentionally not enabled. Prisma connects via the Supabase
  pooler as the `postgres` (table-owner) role, which bypasses RLS
  regardless of policies, and auth is a custom JWT (not Supabase Auth) with
  no `auth.jwt()` claim available to policies. baker_id scoping remains
  fully app-layer, audited across every order/customer/investment/inventory
  query path.
- **`bakers`** absorbed several fields kept for compatibility with existing,
  already-shipped features not in the original redesign spec:
  `merchant_name`, `default_collection_method`, `fssai_document_path`,
  `razorpay_plan_id`, `next_billing_date`, `subscription_plan`, `status`
  (account lifecycle, read by `auth.service.ts` — untouched, values
  preserved byte-for-byte), and a generic `is_verified` flag now kept
  distinct from the new, separate `fssai_verified` (previously the API
  mapped `fssaiVerified` from `isVerified`, conflating two different
  concepts).

## [v0.6.0] — 2026-07-27 — Email OTP Auth Migration

### Changes

#### `Baker` model — Modified

```diff
model Baker {
  id          String   @id @default(uuid())

- firebaseUid String   @unique     // Was required; identity key for Firebase Auth
+ firebaseUid String?  @unique     // Now optional; retained for data compatibility

+ email       String?  @unique     // New primary identity field for Email OTP auth

+ @@index([email])                 // New index for email-based lookups
}
```

**Reason:** Firebase Phone Auth removed. Email is now the primary identity. `firebaseUid` retained as optional for backward compatibility with any existing bakers.

---

#### `EmailVerification` model — New

```prisma
model EmailVerification {
  id         String    @id @default(uuid())
  email      String
  otpHash    String                    // SHA-256 hash of 6-digit OTP; raw OTP never stored
  expiresAt  DateTime                  // 5 minutes from creation
  attempts   Int       @default(0)     // Incremented on each failed verification; max 5
  verifiedAt DateTime?                 // Stamped on successful verification; prevents re-use
  consumedAt DateTime?                 // Single-use timestamp
  lastSentAt DateTime?                 // Cooldown timestamp
  ipAddress  String?                   // Client IP address
  userAgent  String?                   // Client user agent
  createdAt  DateTime  @default(now())
  updatedAt  DateTime  @updatedAt

  @@index([email, createdAt])          // For rate limit queries (count sends within 1 hour)
  @@index([email, expiresAt])          // For verification lookup with expiry check
}
```

**Purpose:** Stores hashed OTPs for the email verification flow. Replaces Redis (previously used in an alternate design). Enables rate limiting, expiry, and audit trail entirely in PostgreSQL.

---

### Migration Notes

- Migration name: `add_email_verification_and_baker_email`
- Applied to: Supabase (via `DIRECT_URL`)
- No data loss: Existing baker records retain their `firebaseUid`; `email` defaults to `null`
- The `email` field must be populated for any new bakers created via the Email OTP flow
